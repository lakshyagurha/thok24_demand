# DxMart Category System — Audit, Taxonomy & Implementation Plan

> **Status:** approved 2026-07-31 · branch `category-taxonomy` · Supabase project `asnjjkpjuqsmjqrjojzl`
> **Phases 1–4 APPLIED to the live project on 2026-08-01.** The database now holds 6 umbrellas
> over 34 shelves, 35 active SKUs across 10 of them, and `category_tree()` serves the whole tree
> to `anon` in one call. `admin-api` is at v4. The audit text below describes the state
> *before* that — it is kept as the record of why, not as a description of today.
> **Audit basis:** live data queried 2026-07-31 over PostgREST, not the migration files.
> Update the checklist at the bottom as phases land.

## Context

DxMart's catalog has **no taxonomy** — it has one flat list of 12 rows in `public.main_category`,
and those 12 names are not umbrella categories at all. They are *Blinkit's L2 subcategory names*
(`Atta, Rice, Oil & Dals`, `Dairy, Bread & Eggs`, `Masala & Dry Fruits`) sitting at the top level
with nothing above them. There is no subcategory table, no `parent_id`, no `sort_order`, no
`is_active`, no `slug`.

The consequences are already visible in the code and the data:

- **8 of the 12 categories hold zero products.** The Category tab renders 12 tiles, 8 of which
  lead to a blank screen.
- **`homeScreen.dart:197-206` hard-codes a string filter** to hide "electronic/appliance/fashion/
  clothing/wear" from the home rail — a taxonomy problem patched in the UI layer, and only in one
  of the three places categories render, so the same category is hidden on Home and visible in the
  Category tab.
- **Products are in the wrong place.** `Taj Mahal Deccan Rose Tea` is filed under *Breakfast &
  Sauces* while an empty *Tea, Coffee & More* sits one tile away.
- **`products.types`** (`normal,Everyday Essentials,Best selling,Hot deals`) is a merchandising tag
  string doing double duty as the only sub-classification the catalog has.

The goal: a real umbrella taxonomy for **grocery and daily essentials**, seeded in Postgres,
reflected in the consumer app so a shopper can navigate the whole shop confidently, and manageable
from the admin app without an engineer.

## STEP 1 — AUDIT (findings)

### 1.1 Current schema

Read from `supabase/migrations/20260724000001_initial_schema.sql` and verified against the live
project `asnjjkpjuqsmjqrjojzl` over PostgREST.

```sql
create table public.main_category (
  id      bigint generated by default as identity primary key,
  name    text,          -- nullable!
  name_hi text,          -- Devanagari
  name_hn text,          -- romanized Hinglish
  image   text
);
-- no parent_id, no slug, no level, no sort_order, no is_active, no created_at
-- no unique constraint on name
-- no index other than the PK

create table public.products (
  id bigint primary key, name text not null, ...,
  main_category_id bigint not null
    references public.main_category (id) on delete cascade on update cascade,
  types text not null default ''    -- comma-separated tag string
);
create index products_main_category_id_idx on public.products (main_category_id);
-- no is_active column: a product can only be removed by deleting it

create table public.banner (
  id bigint primary key,
  category_id bigint references public.main_category (id) on delete set null,
  banner_image text not null
);
```

**There is no subcategories table anywhere.** The hierarchy is one level deep, full stop.

RLS: `main_category_select_all` grants read to everyone; there is **no write policy for any client
role**, so all catalog writes go through the `admin-api` Edge Function using the service-role key.
That design is correct and this plan keeps it.

### 1.3 Every problem found

**Structural**
1. **No hierarchy.** One flat level. The 12 names are L2-grade names with no L1 above them.
2. **No `sort_order`.** Every consumer orders by `id`, so display order is *insertion order*.
   `Frozen Food` (31) sits after `Masala & Dry Fruits` (30) for no reason a shopper can perceive.
3. **No `is_active`.** A category can only be hidden by deleting it (which `on delete cascade`
   turns into deleting its products) or by hard-coding its name into a UI filter — which is
   exactly what `homeScreen.dart` does.
4. **No `slug`.** Nothing stable to address a category by; only integer ids.
5. **`name` is nullable** and has no unique constraint. Nothing stops two `Frozen Food` rows.
6. **`products.is_active` does not exist.** Withdrawing a SKU means deleting it and losing its
   variants, images, order history links and hand-built voice aliases.

**Data quality**
7. **8 of 12 categories are empty** (67%). Four categories hold all 37 products.
8. **Two categories hold 1 product each** after the correct split is applied (see §3.4).
9. **Miscategorised products** — verified by reading all 37 names:
   - `Taj Mahal Deccan Rose Tea` (id 19) is in *Breakfast & Sauces*; *Tea, Coffee & More* is empty.
   - `Khari Foods Kalmi Dates / Khajur` (22) and `Popular Fit Eats Chia Seeds` (17) are in
     *Breakfast & Sauces*; *Masala & Dry Fruits* is empty.
   - `Cake Tale Muffin` (30) and `Theobroma Plum Cake` (31) are in *Dairy, Bread & Eggs*.
   - `Fortune Kachi Ghani Mustard Oil` (8) and `Akshayakalpa Desi Cow Ghee` (6) are correct only
     because category 23's name bundles four unrelated shelves.
10. **`Packaged Food` (34) is a non-category.** Every packaged SKU in the catalog is packaged food.
    It can never be defined against its siblings, so it can never be filled correctly.
11. **Near-duplicate / overlapping names**: `Frozen Food` vs `Ice Creams & More` vs `Packaged
    Food`; `Masala & Dry Fruits` vs the "Oil" inside `Atta, Rice, Oil & Dals`.
12. **Inconsistent naming**: three names end in the filler `& More` / `& Dals`; `Sweet Cravings`
    is a mood, not a shelf; casing is consistent (Title Case) but the `&`-joined compounds run to
    four concepts (`Atta, Rice, Oil & Dals`).
13. **All 295 `product_aliases` have `language = 'auto'`** despite the column existing to
    distinguish `hi` from `hn`. Voice search works, but the column carries no information.
14. **3 of 6 banners have `category_id = NULL`** (ids 3, 4, 5 — orphaned during Phase 5).
    Banner 8 points at category 30, which this plan retires.
15. **3 variants have `selling_price > price`**, so the discount badge computes a negative
    percentage. Out of scope here but worth a one-line fix while the data is being touched.

**Code-level**
16. **`homeScreen.dart:197-206`** hides categories by substring-matching English names. Fragile,
    invisible to the admin, and inconsistent with the other two category surfaces.
17. **`product_management_screen.dart:2572`** renders `'C : ' + product['main_category_name']`,
    but `AdminCatalog.productsWithDetail()` (`admin_api.dart:269-306`) never selects or joins that
    key. **This throws at render time** — it is a live crash in the admin product list.
18. **`product_details_screen.dart:304-306`** reads `_localProduct['subcategory']`,
    `['category_id']` and `['category']` — all PHP-era keys that the Supabase models never
    populate. The "Explore all X's Items" CTA therefore renders with an empty name and navigates
    to `categoryId: null`.
19. **No orphan products in the FK sense** — `main_category_id` is `NOT NULL` with a real FK, so
    the database is referentially clean. The orphaning here is *semantic*, not referential.

### What the research actually says

1. **Two levels of *browsing* is the ceiling.** Every one of these apps shows exactly two levels
   before a product list. BigBasket's third level exists but is reached by filter chips, not by a
   third tap. Depth beyond 3 is a data-modelling concern, not a navigation one.

2. **The L1 umbrella exists to make the grid legible, not to be browsed.** Nobody taps "Grocery &
   Kitchen" and expects products. They tap it and expect *shelves*. This is precisely what DxMart
   is missing: its 12 shelf names have no umbrella to group them, so the Category tab is a wall of
   12 unrelated tiles.

3. **"Other" is a diagnostic, not a category.** The taxonomy literature is blunt about it —
   *"'Other' is a white flag. It admits your category definition didn't quite cover the catalog,
   and it punts the hard decisions onto the shopper."* Blinkit's answer is to give edge products a
   real named home (`Paan Corner`) rather than a bucket.

4. **One primary category, always.** *"Every product should have one primary category — the one
   that determines its attribute template and its place in your core data model."* Secondary
   placement is a **merchandising** concern handled by tags and collections — never by giving a
   product two parents. DxMart already has the right mechanism for this (`products.types`); it just
   isn't named as such.

5. **Seasonal categories never enter the permanent tree.** Blinkit's `Weddings` / `Kids` tabs are
   a contextual layer *above* the taxonomy. Creating and later orphaning permanent nodes is the
   documented anti-pattern.

6. **Left rail beats horizontal tabs for browsing, tabs beat rail for ≤5 peers.** A vertical rail
   shows ~8 siblings at once against ~3.5 for a horizontal strip, keeps the product grid on screen
   while you switch shelves, and puts every target within one thumb arc. Horizontal tabs win only
   when the whole set fits without scrolling.

### Recommendation for DxMart

**Adopt the Blinkit shape, scaled down: 2 browsable levels (L1 umbrella → L2 shelf), with L3
reserved in the schema but not created until a shelf actually outgrows one screen.**

Reasoning specific to this project:

- The existing 12 names are already L2-grade. They need a roof, not a rewrite. Six umbrellas over
  the existing names is the smallest change that fixes the actual problem.
- The audience is Hindi-first households in Sagar/Khurai/Bina. Two taps to any product is the
  budget; three is not.
- The THOK24 charter in `CLAUDE.md` says *"prove cheaply, don't build ahead of proof."* Creating
  L3 nodes for a 37-SKU catalog is building ahead of proof. The `level`/`parent_id` schema costs
  nothing and makes L3 a data change later, not a migration.
- `products.types` already does merchandising tags. Formalise it as the secondary-placement and
  seasonal mechanism instead of inventing a second one.

## STEP 3 — PROPOSED TAXONOMY

### Naming rules enforced

- Title Case. Maximum **one** `&` per name. No `& More`, no `& Dals`, no mood words.
- ≤ 22 characters for every L1 and L2 (verified below; longest is `Beauty & Personal Care` = 22).
- Every node carries `name`, `name_hi` (Devanagari) and `name_hn` (romanized Hinglish).
- Every L1 carries `icon_url`, `sort_order`, `is_active`.
- Maximum depth 3. **Zero L3 nodes are created now** — the rule for adding one is written into
  the admin docs: *create an L3 only when a single L2 exceeds ~40 in-stock SKUs.*
- **No "Others" node exists at any level.** Products that don't fit go to an admin-only
  `Uncategorised` staging node with `is_active = false`, which never renders in the app and shows
  as a work queue in the admin. Current occupancy: **0 SKUs (0.0%)**, against your 2% ceiling.

## STEP 4 — DATABASE PLAN

### 4.1 Schema: extend `main_category` with a self-referencing `parent_id`

**Recommendation: one self-referencing table, not separate `categories`/`subcategories` tables.**

Justification:
- **Depth becomes data, not schema.** Adding an L3 shelf later is an `INSERT`. With separate
  tables it is a migration, a new FK, a new RLS policy, a new admin-api allowlist entry and a new
  admin screen — for every level.
- **One RLS policy, one allowlist entry, one admin screen, one cache key.** The existing
  `main_category_select_all` policy and the `admin-api` `WRITABLE` entry keep working untouched.
- **`products.main_category_id` and `banner.category_id` keep their existing FKs.** A separate
  subcategory table would require repointing both, which is exactly the destructive change you
  asked to avoid.
- **Cycles are structurally impossible** given the level constraint below (`child.level =
  parent.level + 1` forces level to increase strictly, so no cycle can close). No recursive
  integrity check needed.
- The only real argument for separate tables — stronger typing per level — is worth nothing at 40
  nodes and costs a third table the moment L3 appears.

**We keep the table *named* `main_category`.** Renaming to `categories` would mean touching the
admin-api allowlist, `AdminTables.mainCategory`, the RLS policy name, and every `.from(...)` call
for zero functional gain. Cheap cosmetics can wait; the plan notes it as an optional cleanup.

```sql
-- 20260731000001_category_tree_schema.sql

alter table public.main_category
  add column parent_id  bigint,
  add column slug       text,
  add column level      smallint     not null default 2,
  add column icon_url   text,
  add column sort_order integer      not null default 0,
  add column is_active  boolean      not null default true,
  add column created_at timestamptz  not null default now();

-- restrict, not cascade: deleting an umbrella must never silently delete its shelves.
-- (Nothing in this plan deletes anything; this is the guard for future hands.)
alter table public.main_category
  add constraint main_category_parent_fk
    foreign key (parent_id) references public.main_category (id) on delete restrict;

alter table public.main_category
  alter column name set not null,
  add constraint main_category_level_ck   check (level between 1 and 3),
  add constraint main_category_root_ck    check (
    (level = 1 and parent_id is null) or (level > 1 and parent_id is not null)),
  add constraint main_category_selfref_ck check (parent_id is distinct from id);

create unique index main_category_slug_key  on public.main_category (slug);
create unique index main_category_name_key  on public.main_category (lower(name));
create index main_category_parent_idx       on public.main_category (parent_id);
-- Covers the only hot read: "active children of X, in display order."
create index main_category_browse_idx
  on public.main_category (parent_id, sort_order) where is_active;

-- child.level must be exactly parent.level + 1. This single rule also makes cycles
-- impossible, since level would have to increase without bound around the loop.
create function private.check_category_depth() returns trigger
language plpgsql security definer set search_path = '' as $$
declare parent_level smallint;
begin
  if new.parent_id is null then
    if new.level <> 1 then raise exception 'root category must be level 1'; end if;
    return new;
  end if;
  select level into parent_level from public.main_category where id = new.parent_id;
  if new.level <> parent_level + 1 then
    raise exception 'category % level % must be parent level % + 1',
      new.name, new.level, parent_level;
  end if;
  return new;
end $$;
create trigger main_category_depth_check
  before insert or update of parent_id, level on public.main_category
  for each row execute function private.check_category_depth();

-- A product may never hang off an L1 umbrella.
create function private.check_product_category() returns trigger
language plpgsql security definer set search_path = '' as $$
declare lvl smallint;
begin
  select level into lvl from public.main_category where id = new.main_category_id;
  if lvl < 2 then
    raise exception 'products must be filed under a subcategory (level >= 2), not an umbrella';
  end if;
  return new;
end $$;
create trigger products_category_level_check
  before insert or update of main_category_id on public.products
  for each row execute function private.check_product_category();

-- Soft-withdraw a SKU without losing its variants, images, aliases or order links.
alter table public.products add column is_active boolean not null default true;
create index products_active_category_idx
  on public.products (main_category_id) where is_active;
```

> **Leaf-ness** (products only on nodes with no children) is deliberately *not* a hard constraint.
> It would deadlock the day you add an L3 under a shelf that already has products. It is enforced
> in the admin picker (only leaves are selectable) and surfaced by a
> `public.v_category_health` view instead.

### 4.3 Backfill script with dry run

`supabase/tools/category_backfill.py` — modelled on the existing `supabase/tools/cutover_e2e.py`
and `migrate_storage.py`.

```
python3 supabase/tools/category_backfill.py --dry-run     # default; writes nothing
python3 supabase/tools/category_backfill.py --apply       # requires --dry-run to have passed
```

Dry run prints and **exits non-zero** on any of:
- a product that would land on an L1 or on a non-existent node
- a product left in `Uncategorised`, or `Uncategorised` exceeding **2% of active SKUs**
- an L2 whose name exceeds 22 chars, contains two `&`, or is not Title Case
- a category left with `sort_order = 0`, a null `slug`, or a duplicate slug
- an active category with no `icon_url`

Output is a per-product `old → new` diff plus a before/after count table per shelf, so the whole
remap is reviewable before anything is written.

### 4.4 Indexes & query performance

| Index | Serves |
|---|---|
| `main_category_browse_idx (parent_id, sort_order) where is_active` | the entire tree read |
| `main_category_slug_key`, `main_category_name_key` | slug lookup, duplicate-name prevention |
| `products_active_category_idx (main_category_id) where is_active` | shelf product list + counts |
| existing `products_main_category_id_idx` | keep (admin reads unfiltered) |

At 40 nodes the tree is a **single sequential scan of one page**. The whole tree serialises to
roughly 8–12 KB of JSON. `category_tree()` is one round trip, replacing today's `categories()` +
one `productsByCategory()` per tab. Mark it `stable` so Postgres can cache it within a statement,
and cache the payload client-side (§6) — the database is not the bottleneck here, the network is.

## STEP 5 — API PLAN

### 5.1 One RPC returns the whole tree

```sql
create or replace function public.category_tree()
returns jsonb language sql stable security invoker set search_path = ''
as $$
  with counts as (
    select main_category_id, count(*)::int n
    from public.products where is_active group by 1
  ),
  lvl3 as (...),  -- bottom-up jsonb_agg; empty today, works the day L3 exists
  lvl2 as (...),
  lvl1 as (...)
  select coalesce(jsonb_agg(x order by sort_order), '[]'::jsonb) from lvl1 x;
$$;
grant execute on function public.category_tree() to anon, authenticated;
```

Built bottom-up by level so adding L3 needs no rewrite. Returns **all three language variants** —
the client localises via the existing `Category.localizedName()`, so one cached payload serves a
language switch with no refetch (the pattern `categoryScreen.dart:37-38` already documents).

`product_count` is the **active count for the whole subtree**, so the app can render the
*Coming soon* state without a second query per tile.

## STEP 6 — APP UI/UX PLAN

### 6.1 Pattern recommendation

**Home:** L1 section header + L2 tile grid beneath each (Blinkit's home). This is the single
change that makes "we have all the categories" true — a shopper scrolling home sees all six
umbrellas and all 34 shelves without a tap.

**Category browse:** **left vertical rail + right product grid.** Keep the pattern
`categoryViewScreen.dart` already has (its own comments at L232-243 defend it), but fix what the
rail *contains*: today it lists all 12 flat categories; it becomes the **L2 shelves of the current
L1**, with the L1 named in a tappable breadcrumb above it.

Why the rail over horizontal tabs: it shows ~8 shelves at once against ~3.5 for a horizontal
strip; it keeps the product grid on screen while you switch shelves, so comparing two shelves
costs a tap and not a screen transition; and every target sits inside one thumb arc on the left
edge. Horizontal tabs win only when the whole set fits without scrolling — true for our 6 L1s
(hence the home rail stays horizontal) and false for a 7-shelf L1.
